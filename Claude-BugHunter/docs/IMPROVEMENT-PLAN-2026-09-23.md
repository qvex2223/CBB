## P0.1. Ложное подтверждение принадлежности данных

### Подтверждённая проблема

В `engine/authorization_matrix.py::evaluate` вычисляется:

`obs.get("response_owner") == obs.get("object_owner")`

Если оба поля отсутствуют, `None == None` даёт true. Успешный ответ без информации о владельце классифицируется как нарушение прав.

### План

- Требовать явно заданные, валидные идентификаторы владельцев перед сравнением.
- Не считать отсутствующие, пустые или невалидные сведения доказательством принадлежности.
- Для успешного чтения без доказательства владельца или явно подтверждённых чувствительных данных возвращать `INCONCLUSIVE`.
- Проверить соседние переходы: корректный отказ, контроль владельца, несовпадающие владельцы, проверка изменения состояния.
- Не менять глобально смысл любого HTTP 200: исправление относится к доказательству нарушения, а не к успешности транспорта.

### Проверки

- Оба поля отсутствуют: не `VIOLATION`.
- Отсутствует только одно поле: не `VIOLATION`.
- Оба поля `null` или пустые: не `VIOLATION`.
- Разные явно заданные владельцы без другого доказательства: `INCONCLUSIVE`.
- Совпадающие валидные владельцы в deny-expected проверке: положительный результат только по согласованному контракту доказательств.
- HTTP 200 с `{}` не доказывает раскрытие данных.
- Запись без подтверждённого изменения состояния остаётся `INCONCLUSIVE`.

Затрагиваемые файлы: `engine/authorization_matrix.py`, тесты матрицы прав и сквозные тесты результата.

## P0.2. Единый смысл подтверждённой находки

### Подтверждённые проблемы по коду

- `Engine.validate()` вызывает `self.eng.confirm(c, v)`, если агент вернул `real: true`; обязательной проверки PoC-артефакта на этом переходе нет.
- `poc_runtime` проверяет `expect`, но результат выполнения не равнозначен доказательству бизнес-ущерба.
- Генератор authz-spec добавляет `is_finding_if_passes`, `verification_required` и пояснения, однако текущие `poc_runtime`/`evidence` не обеспечивают их смысл как общего исполняемого контракта.
- Для чтения заготовка первоначально имеет только `expect.status=200`; необходимость проверки данных владельца выражена текстом.
- `cbh report` генерирует черновик, но не является универсальным обязательным gate подтверждения. Генерацию черновика не следует смешивать с разрешением на отправку.

### План

- Разделить результат транспорта/сценария и статус доказательства находки.
- Ввести единый путь перевода кандидата в подтверждённое состояние для автономного движка, CLI evidence/triage и stop gate.
- Ответ модели использовать как оценку кандидата, а не как единственное основание для `confirmed`.
- Контрольный запрос владельца может успешно пройти, но не должен стать находкой.
- Доказательство чтения должно содержать проверяемую связь с данными собственного второго тестового аккаунта; доказательство записи — подтверждённое изменение состояния.
- Привязывать артефакт к конкретной проверке, операции, контексту тестового пользователя и запуску. Совпадения host/path недостаточно для различения контрольной и проверяемой операции.
- Проверить связь wire evidence с конкретной находкой: произвольный соседний HAR/Burp-файл не должен подтверждать чужое утверждение.
- При ошибке загрузки механизма доказательств не откатываться незаметно к слабой текстовой эвристике.
- Невалидные или неполные артефакты должны оставаться неполными, а не получать положительный статус по умолчанию.

### Решение перед реализацией

Зафиксировать схему статусов и версионирования артефактов, правила совместимости старых `.result.json` и общий интерфейс проверки доказательств. Не менять существующие реальные артефакты автоматически.

### Проверки

- `real: true` от mock-агента без доказательства не даёт `confirmed`.
- PASS контрольного запроса не учитывается как находка и не удовлетворяет stop gate.
- Правильно отклонённый cross-principal запрос не становится находкой.
- Пустой HTTP 200 не подтверждает раскрытие данных.
- Нерелевантный артефакт для того же endpoint не заменяет доказательство конкретной проверки.
- Испорченный артефакт, неподдерживаемая версия или ошибка evidence-модуля не дают ложного подтверждения.

Затрагиваемые файлы: `engine/engine.py`, `state.py`, `poc_runtime.py`, `evidence.py`, `authorization_matrix.py`, `stop_gate.py`, `cbh/cli.py` и соответствующие тесты.

## P0.3. Ошибка выполнения не должна означать «проверено»

### Подтверждённая проблема

`Engine.hunt()` помечает элемент `tested` до разбора результата агента. `_hunt_agent()` превращает техническую ошибку в `vulnerable: false`. `state.worklist()` исключает tested-элементы при возобновлении.

Следствие: timeout, лимит модели, ошибка конфигурации или неверный формат ответа могут убрать фактически незавершённую проверку из очереди.

### План

- Разделить состояния «не запускалось», «выполняется», «неопределённо», «заблокировано», «получен отрицательный результат», «подтверждено».
- Хранить причину технической ошибки отдельно от предметного результата.
- Не исключать из будущего планирования проверку только потому, что процесс агента завершился.
- Сохранять факт уже отправленного запроса и неопределённого исхода: автоматический повтор изменяющего состояние действия не разрешать без проверки результата предыдущего вызова.
- Определить совместимость с существующим списком `tested`; отсутствие детальных старых данных не превращать в выдуманное доказательство.

### Проверки

- Timeout до отправки запроса не становится отрицательным результатом.
- Ошибка MCP/config и лимит модели сохраняют причину и незавершённость.
- Невалидный JSON агента не означает отсутствие уязвимости.
- После restart/resume незавершённая работа видна.
- Доказанный отрицательный результат не перезапускается бесконечно.
- Неоднозначно выполненная запись не повторяется автоматически.

Затрагиваемые файлы: `engine/engine.py`, `state.py`, `agent.py`, интеграционные тесты возобновления.

## P0.4. Исполнимый контракт PoC и безопасный preflight

### Подтверждённая проблема

`authorization_matrix._auth_headers()` генерирует `{{env:NAME}}`, но `poc_runtime.substitute()` поддерживает только имена без двоеточия и не читает такие переменные окружения. В single-request ветке также требуется проверить единообразие применения подстановок.

### План

- Поддержать объявленные ссылки на переменные окружения в разрешённых полях сценария.
- Не записывать разрешённые значения секретов в spec, результаты, аудит, логи или сообщения об ошибках.
- Сделать обработку placeholders одинаковой для одиночного запроса и многошагового сценария.
- До первого запроса проверять обязательные поля, известные placeholders, наличие переменных окружения и допустимость ожиданий.
- Различать placeholders, которые должны быть заданы заранее, и значения, захватываемые предыдущими шагами.
- После runtime-подстановки повторно проверять фактический URL до отправки: предварительная проверка шаблона не заменяет проверку адреса, полученного из ответа.
- Не разрешать выполнение неподготовленной authz-заготовки только потому, что она синтаксически является JSON.
- При отсутствии данных владельца для verify не подставлять молча контекст действующего пользователя как равноценное доказательство.

### Проверки

- Синтетическая env-переменная действительно подставляется.
- Отсутствующая переменная вызывает понятный отказ до сети.
- Незаданные OBJECT_ID и обязательные verification markers блокируют неподготовленный сценарий.
- Capture предыдущего шага работает без ложного отказа preflight.
- Подставленный URL вне scope блокируется до отправки.
- Чувствительные значения не появляются в сохранённых артефактах и диагностике.
- Локальная цепочка «генератор authz-spec → preflight → исполнение → evidence» работает целиком, а не только создаёт поля с правильными именами.

Затрагиваемые файлы: `engine/poc_runtime.py`, `authorization_matrix.py`, `request_broker.py`, тесты authz-spec и PoC-runner.

## P0.5. Полнота контроля исходящих запросов

### Подтверждённые ограничения

- `_RecordingRedirect` записывает переходы и передаёт их urllib без отдельного вызова broker для нового URL.
- `bbcurl` проверяет извлечённые URL и ждёт pacing перед запуском curl, но это не доказывает контроль каждого запроса внутри запуска.
- `mcp-gate.py` имеет разрешающие ветви при внутренних ошибках.
- MCP-hook не наблюдает все браузерные запросы, вызванные кликами/JavaScript.

### План

- Определить честную границу гарантий для каждого транспорта: что проверяется в коде, что только инструкциями, что недоступно наблюдению.
- Проверять scope, обязательные заголовки и pacing на каждом реальном HTTP-переходе, включая редиректы и URL после подстановок.
- Не переносить аутентификационные данные на другой origin без явно разрешённого контракта.
- Проверить обработку curl-аргументов, batch/multi-URL, редиректов, повторов, URL из конфигурационных источников и закрепления IP. Это область для дополнительных локальных тестов, а не утверждение, что все варианты уже воспроизведены.
- Для запросов к engagement выбирать безопасный отказ при неисправном gate; не ослаблять политики ради прохождения тестов.
- Для браузера выбрать реально контролируемую интеграцию сетевых запросов либо явно исключить неподконтрольные действия из автоматического режима. Не объявлять проблему решённой одним hook на navigation.
- Проверить, какие потребители реально соблюдают max_concurrency: интервал старта запросов и число одновременно выполняющихся запросов — разные ограничения.
- Сохранить правило отсутствия автоматического повторения неоднозначных Burp-вызовов.

### Проверки

Только локальные серверы и mocks: разрешённый/запрещённый redirect, same-origin/cross-origin заголовки, pacing каждого перехода, сбой gate, несколько запросов одного транспорта, общий бюджет процессов, отсутствие повторной отправки после неопределённого результата.

Затрагиваемые файлы: `engine/request_broker.py`, `pacing.py`, `poc_runtime.py`, `scripts/bbcurl`, `scripts/mcp-gate.py`, при согласованном дизайне — `runtime/`.

## P1.1. Единая очередь вместо нескольких параллельных моделей работы

### Подтверждённая проблема по коду

`engine.py` записывает API manifest и workflow, но основной `rank()` использует статические веса классов и свой `surface`, а `hunt()` читает `state.worklist()`. Прямого использования новой очереди vectors, матрицы прав или анализа существенных полей ответов в этом пути нет.

Тест `test_manifest_feeds_vector_seeding` сам вызывает `vectors.seed_from_manifest()`. Он подтверждает совместимость компонентов, но не их автоматическую композицию в основном запуске.

### План

- Выбрать единственный источник состояния запланированных проверок.
- Связать operation, гипотезу, собственные тестовые principals/объекты, попытки и доказательства устойчивыми идентификаторами.
- Подавать manifest/workflow/authz-планы в эту очередь, а не создавать независимый третий планировщик.
- Ранжировать с учётом применимости, готовности тестовых данных, правил программы, новой информации и стоимости проверки, а не только условной тяжести класса.
- Не трактовать отсутствие аккаунта или владельца объекта как отрицательную проверку.
- Принимать изменения поверхности из recon-diff без потери уже выполненной работы.
- Сохранять read-only и default-deny свойства; не включать массовое выполнение новой очереди автоматически.

### Решение перед реализацией

Описать формат задания, владельца состояния, переходы статусов, интерфейс выдачи/завершения задания, совместимость CLI и правила конкурентного доступа. Затем реализовывать минимальную вертикальную цепочку.

### Проверки

Один локальный fixture должен пройти весь путь: импорт API → гипотеза → очередь → допустимая проверка → доказательство → корректный статус → resume без потери или дублирования. Тест должен запускать штатный orchestration entry point, а не вручную соединять отсутствующие связи только внутри теста.

## P1.2. Замкнуть обратную связь по ответам

### Основание

По историческому `eval/README.md` сохранение ответов не гарантировало их анализа: агент мог сделать вывод, не использовав уже накопленное опровержение. Эти исторические результаты в текущей сессии не пересчитывались.

### План

- Перед новой попыткой формировать компактную сводку предыдущих наблюдений по тому же operation/контексту.
- Для гипотезы хранить вопрос, альтернативные объяснения и наблюдение, которое способно различить их.
- Подавать сравнение существенных JSON-полей автоматически в этап решения, а не только по добровольному вызову `cbh diff`.
- Отличать изменения timestamp/nonce/request ID от изменения проверяемого бизнес-результата.
- Учитывать разные users/tenants/методы: не смешивать несопоставимые ответы в одну статистику.
- Использовать уже сохранённые данные без повторной отправки запросов ради визуализации или пересчёта ранее зафиксированного результата.

### Проверки

Локальные fixtures: постоянный decisive field при меняющихся технических полях; реальное изменение состояния; одинаковый endpoint в разных user contexts; отсутствие данных вместо ложного вывода; отсутствие новой сети при чтении корпуса.

## P1.3. Runtime и переносимость ограничений

### Основание

- Hooks зарегистрированы в настройках Claude Code, но их наличие не доказывает выполнение в другом клиенте.

- Добавить безопасный preflight зависимостей, конфигов, разрешения engagement и доступности нужных инструментов.

### Предложение 2026-09-23. Режим бесконечного цикла поиска («нет тупика»)

**Формулировка оператора:** инструмент не останавливается вообще — непрерывно сканирует поверхность, перебирает и ротирует векторы атаки, не знает состояния «больше нечего проверять». Целевой минимум — находки severity medium и выше; находка класса low не закрывается как итог, а дорабатывается (escalation/chain) до уровня medium+, если это возможно. Каждая подтверждённая находка складывается в отдельную папку находок, после чего поиск немедленно продолжается.

**Как это могло бы отображаться на существующие механизмы (гипотеза, не оценено в коде):**

- Непрерывный цикл: построить поверх существующего continuous mode (`hunt-memory/continuous.json`) и stop gate — цикл продолжается по новой очереди векторов, а не по формальному бюджету итераций.
- Исчерпание очереди ≠ остановка: генерация новых кандидатов из vectors (мутации), workflow graph (непроверенные гипотезы), recon-diff (новая поверхность), cve-ledger (неподтверждённые версии).
- Low → medium+: после low-находки автоматический запуск цепочек по таблице сигналов `/chain` (A→B) и проверки escalation-условий до фиксации финальной severity.
- Папка находок: экспорт каждого подтверждённого результата как самодостаточного артефакта (spec + `.result.json` + краткое описание) в `Targets/<name>/findings/`, с дедупликацией, чтобы цикл не «переоткрывал» одну находку.
- Предпосылка: режим осмыслен только после пунктов P0.1–P0.4 и P0.5 — бесконечный цикл с недостоверным подтверждением будет бесконечно производить ложные находки, а с пробелами транспортного контроля — накапливать неучтённые запросы.

**Открытые противоречия, требующие решения до реализации:**

- Правила программ и pacing (`profile.json`, запрет hammering/DoS) задают внешний предел запросов; «бесконечность» упирается в них, а не в код. Цикл обязан уважать бюджет и явную остановку оператора.
- Цели реальные, а не лабораторные: не прогонять этот режим на внешних scope до завершения P0.5 и без разрешения правил конкретной программы.
- Определить критерий «ловушки/тупика»: что делать, когда ни новая поверхность, ни свежие мутации не дают новой информации — снижение частоты, ожидание recon-diff, уведомление оператора вместо холостых запросов.
- Определить, что считается «medium+» до фиксации: оценка impact должна подкрепляться доказательством (P0.2), а не заявлением агента.
- Стоимость: бесконечный цикл расходует запросы и модельные токены без верхней границы; нужен видимый учёт расхода на новую информацию, а не на число итераций.

### Предложение 2026-09-23. Сверка находки с раскрытыми отчётами HackerOne

**Формулировка оператора:** после того как инструмент нашёл находку, он обращается к публично раскрытым отчётам HackerOne, ищет похожие случаи (по классу уязвимости, эндпоинту, признакам поведения), изучает, как атака была реализована в найденных отчётах, и пытается воссоздать аналогичную технику на текущей цели — чтобы доразвить свою находку до формы, в которой она уже была доказана у других.

**Как это могло бы отображаться на существующие механизмы (гипотеза, не оценено в коде):**

- Инструмент уже содержит ~681 паттерна из раскрытых отчётов по 24 классам уязвимостей (по README) — предложение превращает статичную библиотеку в живой шаг: поиск похожих отчётов запускается в момент находки, а не только до охоты.
- Точки подключения: после перехода в `confirmed` (или на этапе escalation low→medium из предыдущего предложения) — запрос к корпусу раскрытых отчётов по классу/признакам находки; затем извлечение из похожего отчёта воспроизводимой цепочки шагов; затем попытка адаптации этой цепочки к текущей цели через существующий `poc_runtime` (только в рамках scope и pacing).
- Связь с внутренней памятью: средство уже имеет `hunt-memory/patterns.jsonl` и `technique_classifier` — внешние отчёты могли бы дополнять тот же слой паттернов, не создавая параллельного хранилища.
- Кандидат на роль источника: публичные страницы раскрытых отчётов HackerOne (activity/хронология, severity, класс, CWE, методология), либо уже собранные корпуса раскрытых отчётов, если они у оператора есть локально.

**Открытые вопросы, требующие решения до реализации:**

- Источник данных: это HTTP-доступ к hackerone.com (публичный контент, но возможные rate limits и ToS сайта), локально зеркалированный корпус или существующий датасет раскрытых отчётов; безопаснее начать с локального корпуса.
- Классификация схожести: по чему подбирать «похожий» отчёт — класс, CWE, стек, тип эндпоинта, текстовое сходство; нужен порог качества совпадения, иначе шаг будет притягивать нерелевантные методики.
- Граница «воссоздания»: новая цепочка шагов из чужого отчёта всё равно обязана проходить общий контракт доказательств (P0.2) — чужой успех не является результатом на текущей цели.
- Контроль выполнения: попытки воссоздания — это новые запросы; они должны идти через `bbcurl`/`poc_runtime` и учитываться в общем бюджете, поэтому шаг зависит от P0.5.
- Юридическая/этическая граница: использование публично раскрытых материалов для методологии допустимо; нельзя переносить чужие секреты, токены или exploits-артефакты, не относящиеся к технике.
- Приоритет: шаг усиливает уже найденные находки; он вторичен относительно исправления ложных подтверждений и восстановления незавершённых проверок (иначе инструмент будет «доразвивать» ложные результаты).

**Пробный прогон 2026-09-23 (выполнен, только чтение публичных страниц):**

- Доступ: логин не требуется, отчёты со статусом «Disclosed» открываются анонимно. Аккаунт оператора не использовался — он и не нужен для публичной ленты.
- `webfetch` не подходит: HackerOne — JS-приложение, без браузера отдаёт пустышку. Использован существующий Playwright MCP runtime инструмента — это важная находка: **не нужен новый компонент, браузерный слой уже в составе bundle**.
- Лента `hackerone.com/hacktivity?queryString=disclosed:true` после ожидания рендера отдала список отчётов с URL и заголовками через простой DOM-запрос (`a[href*="/reports/"]`).
- Отчёт #4020767 («Unauthenticated API…») содержит полностью пригодную для автоматизации структуру:
  - Summary → описание поверхности;
  - Root cause → **таблица `route × methods × authentication`** — готовая карта поверхности API;
  - Impact → классификация последствий (read/write/delete);
  - PoC → **пошаговые curl-команды** с ожидаемыми ответами (HTTP-статусы, тела), включая описание контрольных проверок;
  - Severity → CVSS 9.3 в явном виде; метаданные страницы: Weakness «Misconfiguration», статус Resolved, дата раскрытия.
- Вывод по осуществимости: **извлечение работает**. Цепочка «лента → отбор по weakness/severity → текст отчёта → curl-шаги из PoC» реализуема на существующих компонентах; curl-шаги по смыслу конвертируются в спецификации `poc_runtime` (шаги + ожидания), а контракт evidence требует только замены прямого curl на вариант через `bbcurl`/`poc_runtime`.
- Ограничения, выявленные прогоном:
  - цели и часть идентификаторов в отчётах замазаны (`████████`), поэтому перенос — адаптация техники, а не буквальное копирование;
  - структура отчётов не унифицирована: у другого отчёта PoC может быть прозой или отсутствовать; экстрактор обязан уметь отказаться («нет воспроизводимой цепочки»), не выдумывая шаги;
  - лента пагинирована и догружается скриптами — сбор нужно троттлить как обычный web-scrape (это не наш scope/pacing, но rate limits HackerOne уважаются).

**Статус:** пожелание подкреплено пробным чтением публичных отчётов — осуществимо на существующих компонентах. Реализация (конвейер извлечения, отбор по схожести, конвертация в PoC-спеки) не начата и не планируется без отдельного решения оператора.
