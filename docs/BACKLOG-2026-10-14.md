# Backlog 2026-10-14 — gaps found by auditing this workspace against the 2026 agentic-hunting consensus

Source of the comparison: the operator's research digest (HackerNotes ep. 166 / rez0, securitycipher
AI bug-bounty workflow 2026, buildmvpfast r/bugbounty roundup, rez0+xssdoctor hackbot post-mortem,
Anthropic red-team zero-day write-up). Everything the digest recommends is already implemented here
except the items below. Ranked by expected return, highest first.

Context for all five: the enforcement layer (scope, pacing, skill gate, stop gate, evidence) is
complete and tested. The measured gap is between **3678 fired requests** (`hunt-memory/audit.jsonl`)
and **2 confirmed patterns** (`hunt-memory/patterns.jsonl`), 29 journal rows, 5 findings, 2
`.result.json`. These five items target that ratio, not new attack coverage.

---

## 1. A falsification pass as its own step — `cbh refute <finding.md>` — DONE 2026-10-14

**Why.** rez0 and xssdoctor cut their false-positive rate from 80% to 60% with a separate bot whose
reward was *disproving* a finding rather than confirming it. This workspace has the Attacker role in
`/parallel` and the `triage-validation` skill, but nothing deterministic runs against every finding,
and both are model-driven — the same model that produced the finding is asked to doubt it.

**How to apply.** New subcommand reading the finding's `.result.json` and firing the controls through
`engine/request_broker.py` (so scope, pacing, mandatory headers, audit and the response corpus all
apply unchanged):

* the same vector against an object the tester owns — a PASS here means the endpoint is public or the
  control was never the thing being tested;
* the same request with the payload removed — a PASS means the baseline already did this;
* the same request as a second principal — fixes the direction of the authorization claim.

A PASSing control kills the finding. Wire the verdict into `engine/evidence.py` so `cbh triage` and
`/validate` read it, and have the verdict demote the finding to `leads/` (item 2) rather than deleting
it. Reuses `sweep.py`'s classification rules; no new transport.

## 2. The missing funnel tiers — `leads/` and `primitives/` — DONE 2026-10-14

**Why.** The digest's note funnel is notes -> leads -> primitives/gadgets -> findings -> reports, and
each tier is what keeps partial progress from being lost to compaction. Here only `notes.md`,
`hosts/` and `findings/` exist. The rule itself is already recorded in the operator's memory
("impact unproven = lead/primitive only, never a finding") with nowhere to put the result, so an
unproven primitive either dissolves into prose in `notes.md` or lands in `findings/` and inflates its
own severity — the exact pressure `engine/stop_gate.py` warns about.

**How to apply.** Add `Targets/_TEMPLATE/leads/` and `Targets/_TEMPLATE/primitives/` with `.gitkeep`,
then teach the readers that a lead is not a finding: `engine/stop_gate.py` must not count a lead
toward the severity bar, `cbh view` should render the tiers as separate columns, and `cbh triage`
should offer the demotion path. Cheap, and it gives item 1 somewhere to put what it kills.

## 3. A no-skills free-roaming agent, then diff the two — DONE 2026-10-14

**Why.** The digest's two-agent trick is specifically asymmetric: agent A gets the full skill set and
methodology, agent B gets only the URL and the authorization, then you paste A's output into B's
session and ask what each one missed. What the free agent found gets promoted into a skill. Every
role in `/parallel` today is a skilled role, so the comparison that makes the trick work cannot
happen — N skilled hunters share one blind spot, which is the thing `/parallel` already warns about.

**How to apply.** The mechanism exists: `engine/agent.py` already runs workers with a fixed
`ALLOWED_TOOLS` and `skills_on=False`, so skills genuinely cannot load. Add a `freeroam` role that
receives the target URL and the identity and nothing else, plus a merge step that reports the
symmetric difference of the two runs. Feed whatever only `freeroam` found into `engine/learn.py`,
which already looks for findings matching no known pattern.

## 4. Bind the browser's storage state to the engagement identity — DONE 2026-10-14

**Why.** The hackbot post-mortem's sharpest number: at one point 80% of tokens went to logging in,
and the money is behind the login. `runtime/playwright-mcp.mjs:10` already passes
`--storage-state` when `CBH_PLAYWRIGHT_STORAGE_STATE` is set, and `engine/identity.py` already
self-provisions identities, but nothing connects them — no caller sets that variable from
`Targets/<name>/identity.json`, so every session re-authenticates from zero.

**How to apply.** Resolve the engagement in the wrapper and default the variable to
`Targets/<name>/identity.json`'s state path; have `identity.py` save the state after a successful
registration or login, and re-save on refresh. Treat the state file as credential material: it is
already covered by the `Targets/*/evidence/`-style ignore rules, keep it that way.

## 5. Write down the subagent cap — DONE 2026-10-14

**Why.** The digest is explicit that an overnight run should use no more than two or three
subagents, because at four or more compaction can break in a way that leaves nothing to roll back
to. That number appears nowhere in this workspace.

**How to apply.** One line in `commands/parallel.md` and one in `commands/autopilot.md`. State the
cap and the reason, so a future fan-out does not rediscover it.

## 6. Replace the dead Burp stack with Caido — DONE 2026-10-14, one operator step left

**Why.** This item was first rejected on the grounds that Burp MCP already covers the last mile.
That was wrong, and the audit that followed says so plainly: `/opt/Claude/tools/burp` does not
exist, `node runtime/health.mjs` reports `burpmcp` as `failed` with
`SSE error: TypeError: fetch failed: connect ECONNREFUSED 127.0.0.1:8181`, `hunt-memory/audit.jsonl`
contains zero Burp references, and no `*.burp.*` or `*.har` evidence file exists under `Targets/`.
Burp here covers nothing, so there is no duplication to avoid.

Caido suits this box better on three counts. Its server ships as a standalone `caido-cli` binary (or
a Docker image) and serves its UI over the browser, which removes the Xvfb display and the
`RobotTool.class` EULA-wizard clicker in `scripts/burp-mcp.sh` — the most fragile part of the bundle
and currently the dead part. Burp Community cannot save project files, so named replay sessions do
not survive a restart, which is precisely the reproducibility the digest credits Caido with. And the
Caido MCP server exposes more than `runtime/burp-bridge.mjs` does: traffic intercept and forward,
HTTPQL filtering over history, sending through Replay, listing Automate and Replay sessions,
retrieving request and response data, creating findings and scope presets, and browsing the Sitemap.

**Correct the premise while doing this.** There is no official Caido *hunting* skill. What
`caido-community` publishes is `caido-plugin-dev`, which covers plugin development. The Caido MCP
server is documented by Caido but labelled community-built, with an explicit note that it is not
affiliated and that its code should be reviewed before installing. So this is a proxy plus a
third-party MCP server, not a vendor-supported skill.

**Status.** Done the same day, except the login. `caido-cli` v0.58.3 runs headless on
127.0.0.1:8080 with `--no-sync`; `caido-mcp-server` v4.3.0 was built here from reviewed source;
`runtime/caido-mcp.mjs` and the `caido` entry in `.mcp.json` are wired; `scripts/mcp-gate.py` gates
every Caido sender (20 new cases in `tests/test_mcp_gate.py`, 377 tests pass). Full write-up:
`docs/caido.md`. **Remaining:** `caido-mcp-server login` is an OAuth device flow against
dashboard.caido.io and needs the operator's Caido account; until that token exists the MCP server
exits with `no authentication token found`.

**How it was applied.**

1. Review the MCP server's source before installing it. It receives every request in the project,
   including live sessions, tokens, and hosts belonging to other programs. Keep one Caido project
   per engagement so two programs' traffic never share one history.
2. Install `caido-cli` headless and add it to `.mcp.json` behind a wrapper in `runtime/`, matching
   how `burp-bridge.mjs` and `playwright-mcp.mjs` keep tool names and timeouts stable.
3. Add the Caido tool-name prefix to `scripts/mcp-gate.py`. Until that branch exists, Caido calls
   bypass the scope gate, the pacing budget, and `audit.jsonl` — the same hole Burp would have had.
4. No change is needed for the WIRE-UNPROVEN rule: Caido exports HAR, which `engine/evidence.py`
   already accepts beside a finding.
5. Decide whether `scripts/burp-mcp.sh` and `runtime/burp-bridge.mjs` stay. Keeping a second dead
   proxy path is what produced this mistake in the first place.

## The cron, and why it was worth nothing before (2026-10-14)

`crontab -l` said `no crontab for qvex`, but installing the jobs as they stood would
have changed nothing, and that is the more useful half of the finding. The workspace
moved from `/opt/Claude/BugHunter` (engagements beside it at
`/opt/Claude/Targets`) to `~/security-research/BugHunter` with `Targets/`
**inside** the bundle — and eleven scripts had the old layout written into them, as a
literal `/opt/Claude/Targets` or as `parents[2] / "Targets"`, which means the same
thing.

None of them crashed. `cve_watch.py` resolved `Targets/<name>` under a root that does
not exist and reported "no watchlist"; `cve-digest.py` fell through its candidate list;
`pattern-analytics` and `technique_classifier` defaulted to an empty corpus at
`/opt/Claude/hunt-memory/patterns.jsonl`. Every one exited 0 or 2 with a plausible
message. A wrong path that is wrong the same way everywhere reads as an empty
workspace, which is why a scheduled run would have been a no-op that logged success.

So the fix came first:

* **`engine/paths.py`** — one resolver (`targets_root()`, `memory_dir()`,
  `template_dir()`), honest about which of the three layouts it found, with
  `$CBH_TARGETS_ROOT` / `$CBH_MEMORY_DIR` overriding. Run it to see what resolved.
* repointed at it: `cve_watch.py`, `cve-ledger-backfill.py`, `cve-digest.py`,
  `program-scaffold.py`, `standoff-scaffold.py`, `intigriti-scope-truth.py`,
  `intigriti-scope-audit.py`, `intigriti-validate.py`, `pattern-analytics.py`,
  `engine/technique_classifier.py`.
* **`scripts/cve-boot-catchup.sh`** rewritten: it had `kcell` and `kcell-main` named
  in it — engagements that do not exist here — and wrote the digest to
  `/opt/Claude/Targets/CVE-DIGEST.md`. It now resolves `Targets/` through
  `engine/paths.py` and **discovers** every engagement carrying a
  `recon/cve-watchlist.txt`, nested `platform/program/` folders included, so a new
  program is watched without editing the script and a deleted one stops being a
  silent no-op. Backup: `scripts/cve-boot-catchup.sh.bak-20261014`.

Then the cron, two entries running the same idempotent script (stamps in
`logs/stamps/`, 20h staleness window, so the boot run and the daily run no-op each
other):

```
@reboot    scripts/cve-boot-catchup.sh >> logs/cve-boot-catchup.log
0 7 * * *  scripts/cve-boot-catchup.sh >> logs/cve-boot-catchup.log
```

`cron` is running and enabled (`/usr/sbin/cron -f -P`, `systemctl is-enabled cron` =
enabled), and the box is no longer WSL, so the overnight-is-off reasoning behind the
old 02:30 slot is gone — 07:00 plus the boot catch-up covers a laptop that sleeps.
Verified by running the script by hand: it regenerated `docs/cve-coverage.md` and
`Targets/CVE-DIGEST.md`, and reported `cve_watch: 0 engagement(s) with a watchlist`,
which is correct — no engagement has fingerprinted a product yet.

**Not scheduled, deliberately:** `scripts/install-recon-snapshot.sh`. It only diffs
manifests that `cbh recon` already produced, and no engagement has one yet, so the
entry would be a no-op with a log file. Install it per engagement once recon output
exists. And nothing is scheduled that sends a request at a live program — that stays
a manual decision, as the installer itself says.

**Still open, and now the only item on this list:** `/remember` is not being called —
2 rows in `patterns.jsonl` against 3678 requests in `audit.jsonl`. Nothing automatable
fixes that; it is a habit during the hunt, and `learn.py`/`pattern-analytics` are worth
exactly what gets fed to them.
